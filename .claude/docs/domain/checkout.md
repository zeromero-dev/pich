# Ordering (Checkout)

Turning a cart draft into a paid order in the CRM. The CRM is the order system of record; this app owns the *process*: validation → payment → order creation. **Current state: the UI flow is built; submit is a fake `setTimeout` in `components/checkout/checkout-view.tsx`. Everything below "Spec" is not built.**

## Model

```
OrderRequest {                        // what the client submits
  items: { workId, qty }[]            // ids only — never prices
  contact: { name, email, phone }
  delivery: { city, address }
  locale                              // for any customer-facing messaging
}
Order {                               // what we create in the CRM
  order_id      generated by us — no DB, so UUID or timestamp-based; must be unique, we are the only writer
  lines         re-derived server-side from fresh CRM data
  total         Σ line totals, computed server-side
  status        "pending" initially (CRM default)
}
```

## Business rules

1. **The client sends intent, not facts.** Only work ids and quantities cross the boundary. Prices, names, and totals are re-derived from fresh CRM data server-side. A price mismatch between what the buyer saw and current CRM data is a *decision point* (reject vs honor), not something to silently absorb — see open decisions.
2. **Stock validation is checkout-time truth.** Each work must be currently available; qty > 1 of any work is rejected (one-original rule, [catalog.md](catalog.md)). Displayed stock was advisory; this check is authoritative.
3. **Payment strictly precedes order creation.** Decided 2026-08-06. An unpaid order must never appear in the CRM; a failed payment produces nothing. (Consequence: a paid-but-order-creation-failed state is possible — it must be loud: log + surface to the buyer with a reference, never swallowed.)
4. Validation UX rule: validate on blur, re-validate on change after first error ("reward early, punish late"). Required: name, email (format-checked), phone, city, address.

## Spec: the flow (`app/api/checkout/`, planned)

```
1. Receive OrderRequest
2. Fetch fresh works from lib/hugeprofit/ (bypass cache or accept ≤5-min window? — open decision)
3. Validate: all works exist, available, qty == 1, contact fields present
4. Compute total server-side
5. PaymentProvider.pay(...) — see below
6. On success: POST /bapi/remote_orders
7. Return confirmation (order_id) → UI success state, cart cleared
```

### Payment provider — the one deliberate interface

The provider (LiqPay / monobank / Fondy / WayForPay) is undecided, so payment is specced as a swap point and built as a stub until then:

```
PaymentProvider {
  initiate(order_id, amount_uah, description) → redirect URL | client token
  verify(callback payload) → paid | failed        // server-side verification, never trust the client redirect
}
```

Most Ukrainian providers are redirect/callback shaped — expect a webhook/callback route when this becomes real. The stub today: checkout succeeds without payment and says so ("Оплату буде додано незабаром").

### CRM mapping — `POST /bapi/remote_orders` (from the API docs, unverified live)

| CRM field | Source | Notes |
|-----------|--------|-------|
| `order_id` | generated by us | required |
| `price`, `currency` | server-computed total, `"UAH"` | required |
| `first_name`, `last_name` | split from the single `name` field | first word / rest — crude but adequate; `first_name` required |
| `phone`, `email` | contact | optional in CRM, required by our rule 4 |
| `address_1` | delivery (city + address) | API docs call it a `RemoteAddressType` object — exact shape needs live verification |
| `order_data[]` | per line: `product_id`, `sku`, `name`, `quantity`, `price`, `total` | from fresh CRM data, not the cart |
| `status` | omit → `"pending"` | status flow after payment — open decision |
| `info` | payment reference | so the owners can match payment to order |

Response includes `reservedProducts` — suggests the CRM reserves stock on order creation; verify live.

## Open decisions

- Stale-price policy at validation (reject and re-show vs honor CRM price silently). Recommendation: reject with a clear message — art prices are significant sums.
- Fresh fetch vs ≤5-min cache window at validation. Recommendation: fetch fresh for the order's works only (`product_id` filter).
- Order status after successful payment: leave `"pending"` or set a paid status? Depends on the owners' CRM workflow (needs `reference_info` / live account).
- Sales-channel tagging of shop orders (CLAUDE.md open decision).
